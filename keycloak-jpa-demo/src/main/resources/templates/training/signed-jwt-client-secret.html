Signed JWT with Client Secret.

Keep the familiar OAuth client secret, but stop sending that secret directly as the client credential on every token request.

Instead, the application uses the secret as an HMAC signing key to create a short-lived JWT client assertion. Keycloak independently calculates the expected signature using the same shared secret.

Concept

What Problem Are We Solving?

Traditional client-secret authentication sends a reusable credential with the token request. Signed JWT with Client Secret keeps the shared-secret trust model but changes how the client proves possession of that secret.

Cryptography

What Does HS256 Mean?

HS256 means HMAC using SHA-256. HMAC is a keyed message authentication mechanism: the same secret is used to generate and verify the authentication code.

Input

JWT Header + Payload

The encoded JWT header and claims form the message being authenticated.

Secret

Client Secret

The OAuth client secret becomes the cryptographic HMAC key.

Output

HMAC Signature

Keycloak can independently calculate and compare the expected signature.

Conceptual Operation

HMAC-SHA256 

HMAC-SHA256(
    base64UrlEncode(header) + "." + base64UrlEncode(payload),
    client_secret
)
Assertion Anatomy

What Is Inside the Client Assertion?

The client assertion is still a JWT. It contains a header, claims describing the client and intended authorization server, and a cryptographic signature.

Part 1

Header 

{
  "alg": "HS256",
  "typ": "JWT"
}

Tells Keycloak which signing algorithm was used.

Part 2

Payload 

{
  "iss": "supplier-service",
  "sub": "supplier-service",
  "aud": ".../token",
  "iat": 1790438400,
  "exp": 1790438460,
  "jti": "unique-id"
}
Part 3

Signature 

HMACSHA256(
  encodedHeader + "." +
  encodedPayload,
  client_secret
)

Proves knowledge of the shared client secret.

JWT Claims

Claims Keycloak Evaluates

The JWT is more than a signature container. Its claims establish who created the assertion, who it represents, where it is intended to be used and how long it should remain valid.

Claim Meaning Typical Value Why It Matters
iss Issuer supplier-service Identifies the client creating the assertion.
sub Subject supplier-service Identifies the client being authenticated.
aud Audience Keycloak token endpoint Restricts where the assertion is intended to be accepted.
iat Issued At Current timestamp Establishes when the assertion was generated.
exp Expiration Short time later Limits the useful lifetime of the assertion.
jti JWT ID Unique value Gives the assertion its own identifier and can support replay defenses.

Critical Distinction

The Client Secret Still Exists

This authentication method does not eliminate the client secret. It changes the role that the secret plays.

Security Model

Why Make the Assertion Short-Lived?

The signed assertion is intended to be ephemeral. Claims such as expiration, audience and JWT ID reduce the usefulness of a copied assertion outside its intended context.

Short Lifetime

iat and exp constrain when the assertion should be accepted.

Audience

aud binds the assertion to its intended authorization-server endpoint.

Unique JWT ID

jti provides a unique identity for an individual assertion.

Fresh Assertion

Generate a new assertion for a new authentication operation instead of treating it as a reusable long-lived credential.

Enterprise Security

What This Does — and Does Not — Solve

Signed JWT with Client Secret changes the authentication protocol, but the underlying secret remains a sensitive shared credential.

Security Consideration Effect
Client secret directly transmitted as parameter Avoided in the JWT assertion model.
Shared secret still exists Yes. Both client and Keycloak depend on it.
Secret storage still required Yes. Protect it like any other high-value credential.
Secret rotation still required Yes. Moving to JWT assertions does not remove lifecycle management.
Assertion lifetime can be short Yes. This reduces the useful lifetime of a captured assertion.
Asymmetric separation No. Unlike private_key_jwt, the verifier still possesses the same secret used by the signer.
Troubleshooting

When Keycloak Rejects the Assertion

Debug the assertion systematically rather than treating every failure as a generic OAuth problem.

Decode the JWT header and verify that the algorithm matches the client authentication configuration. 
{
  "alg": "HS256",
  "typ": "JWT"
}

HMAC verification requires both parties to use the same secret. A rotated or stale application secret causes signature verification to fail.

Verify that the assertion identifies the intended Keycloak client. 
"iss": "supplier-service",
"sub": "supplier-service"

Verify that the assertion was created for the expected Keycloak token endpoint. Do not blindly copy an audience value from another environment.

Confirm that the assertion is currently valid and that application and Keycloak system clocks are reasonably synchronized.

The request needs the JWT bearer client assertion type: 
urn:ietf:params:oauth:client-assertion-type:jwt-bearer

A perfectly signed JWT can still be embedded in an incorrectly constructed HTTP request. Verify:
  • Token endpoint URL
  • Content-Type
  • grant_type
  • client_id
  • client_assertion_type
  • client_assertion
Architecture Perspective

Where Does This Model Fit?

Signed JWT with Client Secret can be useful when an application already operates with client secrets but you want assertion-based authentication without immediately introducing asymmetric key management or certificate infrastructure.

Migration

Move from direct client-secret presentation toward assertion-based authentication.

Short-Lived Proof

Generate authentication assertions with explicit issuance and expiration times.

Existing Secrets

Continue using established secret-management infrastructure.

No PKI Dependency

The HMAC model does not require a public/private keypair or X.509 certificate lifecycle.

Key Takeaway

Same Shared Secret — Different Proof

Signed JWT with Client Secret does not eliminate the shared secret.

Instead of presenting the reusable secret directly as the OAuth client credential, the application uses it as an HMAC key to sign a short-lived JWT assertion. Keycloak possesses the same secret, independently calculates the expected signature, validates the JWT claims and authenticates the client before issuing the access token.
