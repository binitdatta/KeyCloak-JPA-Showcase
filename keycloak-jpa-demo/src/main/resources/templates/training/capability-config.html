OAuth Client Capability Configuration.

One Keycloak client can expose very different OAuth capabilities depending on which switches are enabled. In this episode we test two fundamentally different authorization models: Client Credentials and OAuth 2.0 Device Authorization Grant.

The first authenticates an application. The second ultimately authenticates a human user even when the originating device has a poor keyboard or browser experience.

Core Concept

OAuth Grant Types Answer Different Trust Questions

A grant type is not merely a different parameter sent to the token endpoint. It describes the security context under which authorization is being obtained.

Capability 02

OAuth 2.0 Device Authorization Grant

Device Authorization is designed for an application running on a device that can communicate over HTTP but may not provide a convenient browser or keyboard. The authentication experience is therefore split across two devices.

Why It Exists

The Device Should Not Need Your Password

Device Authorization separates the device requesting access from the browser in which the person authenticates. That distinction is the core architectural idea.

Limited Device

The originating device may have no keyboard, inconvenient input or no practical browser.

User Code

The device displays a short code that the person can enter or follow through a verification URL.

Trusted Browser

The person performs the actual Keycloak login using a browser-capable device.

Human Token

After approval, the originating device receives tokens representing the authenticated user.

End-to-End Device Flow

Follow Every Step

Unlike Client Credentials, Device Authorization is asynchronous: the device begins the flow, waits while a human authenticates elsewhere, and polls Keycloak until authorization succeeds or the request expires.

Important Distinction

device_code Is Not user_code

The Device Authorization response contains two codes because they serve different actors in the protocol.

Machine-Facing

device_code

The originating device retains this value and presents it while polling the token endpoint.

Actor: Device / Application
Human-Facing

user_code

This shorter value is intended to participate in the human verification and approval experience.

Actor: Human User
Asynchronous Behavior

The Device Is Waiting on a Human Event

The device does not know when the person will complete authentication. Polling bridges that asynchronous gap.

State Meaning Device Behavior
Code Issued Keycloak created the device authorization request. Display instructions to the user.
authorization_pending The person has not completed authorization yet. Continue polling according to the configured interval.
Approved The user authenticated and approved the request. Token endpoint can return tokens.
expired_token The authorization window ended before successful completion. Stop polling and begin a new device flow if appropriate.

The client initiated the flow, but the resulting token represents the authenticated person.

Troubleshooting

Common Failure Points

Separate configuration failures from protocol-state failures. The two grant types fail for very different reasons.

Confirm that the client is configured for authentication and that service accounts are enabled. Also verify the client ID and credential used in the token request.

Inspect the service-account user's role assignments and the client's role mappings rather than assuming the machine identity has the same permissions as a human administrator.

Verify that OAuth 2.0 Device Authorization Grant is enabled for the client before debugging the curl request itself.

This does not necessarily mean the flow failed. It means the authorization process has not yet completed. Verify that the user opened the correct verification URI, authenticated and approved the request.

The original test returned: 
"expires_in": 600

If the user does not complete the flow before the authorization request expires, begin a new Device Authorization flow.

Respect the polling interval supplied in the device authorization response. The tested response contained: 
"interval": 5
Practical Architecture

Match the Grant to the Actor

The simplest way to distinguish these flows is to ask whose identity the protected API actually needs.

Scheduled Job

No person is present. The job should authenticate as a machine identity.

Client Credentials

Microservice

One backend service needs to call another using its own application identity.

Client Credentials

Smart TV

A person needs to authorize an application on a device with inconvenient credential entry.

Device Grant

CLI Application

A command-line application can initiate the flow while authentication occurs through a browser.

Device Grant
Key Takeaway

Client Capabilities Change the Trust Model

The important question is not simply: “Did Keycloak return a token?”

Client Credentials answers: “Which application is this?” Keycloak represents that application through its service-account identity. Device Authorization answers: “Which person approved access?” The originating device never needs to collect that person's credentials; authentication occurs through the browser-capable device, and the resulting token represents the human user.
