How SAML Single Logout works

A user who signs in through Keycloak and Microsoft Entra may have separate sessions: one in your Spring Boot application, one in Keycloak, and one in Entra. Ending one session does not automatically end the others.

  1. Front-channel logout: a browser carries redirects or SAML logout messages between the participating systems. This is visible to the user's browser and can be affected by redirects, cookie rules, or a closed tab.
  2. Backchannel logout: participating servers exchange logout messages directly, without requiring the browser to deliver each message. Protocol support matters: SAML Single Logout may use bindings such as SOAP when implemented by both partners; OIDC back-channel logout is a distinct mechanism.
  3. What “Off” means here: the provider-specific backchannel option is disabled. It does not mean that logging out of the browser, Keycloak, Entra, and downstream apps is guaranteed to happen together.

Example: you click Logout in Spring Boot. Its local session ends. A Keycloak logout may also run. Whether Entra's session and other application sessions end depends on configured Single Logout integration—not just this one toggle.

NameID, Persistent NameID, and Subject NameID

NameID is the identity value asserted by the SAML Identity Provider for the authenticated person. It lives inside the <Subject> of the SAML assertion. For example:

<saml:Subject>
  <saml:NameID Format="urn:oasis:names:tc:SAML:2.0:nameid-format:persistent">
    user-opaque-12345
  </saml:NameID>
</saml:Subject>

Persistent is the requested format. It aims for a stable, non-human-readable identifier for a user at a particular service provider. Unlike email, that identifier can remain stable if a person changes their email address. It is not guaranteed by merely choosing the format; verify the assertion returned by Entra.

Subject NameID is the source Keycloak uses as the principal: it tells Keycloak to read the value from the incoming assertion’s Subject/NameID. It does not select the Persistent format; that is the separate NameID policy setting.

Important: a change in NameID can affect how a returning external user is recognized. Test account linking and the user identifier strategy carefully before changing these settings in an existing federation.

HTTP-POST binding versus Artifact binding

HTTP-POST response: Entra returns a browser form containing an encoded SAMLResponse. The browser posts that form to Keycloak's ACS endpoint, where Keycloak validates it.

HTTP-Artifact response: the browser carries a short reference rather than the whole assertion. Keycloak then contacts an Artifact Resolution Service directly to obtain the real SAML message. That requires both providers to support the flow and a configured artifact resolution endpoint.

In these screenshots, HTTP-POST is On and ARTIFACT response is Off, so the usual browser-posted SAML response is expected.

What “Pass subject” would send

Imagine your application already knows the user identifier and initiates a new federated sign-in. With a suitable subject available, Keycloak may include it as a hint inside the outgoing SAML AuthnRequest. The external IdP still must authenticate the user and issue a valid response.

Off means this subject-forwarding behavior is not used in the demonstrated configuration. This setting is separate from Subject NameID, which controls how Keycloak reads the identity returned by the IdP.

How these broker settings work together

Example: Susan authenticates with Microsoft Entra ID, which sends a valid SAML response to Keycloak. Keycloak resolves the external user identity (typically based on IdP alias and incoming NameID) and checks for an existing broker link.

  1. First-time user: If no broker link exists, Keycloak invokes the configured first login flow override. The flow may require account creation, linking or additional verification depending on its configured executions. Account linking only = Off means creation is not categorically prohibited by that option.
  2. Returning user: Keycloak can reuse the existing broker identity link. The post login flow, if configured as shown, can perform further checks before returning to the application.
  3. Attribute synchronization: Sync mode = Legacy influences how brokered account data is synchronized; it does not mean every mapped attribute is refreshed unconditionally.
  4. Email handling: Trust Email = Off avoids implicitly setting email verification merely on the basis of the external claim.
  5. Tokens and visibility: The token switches govern retention/access to external broker tokens; they do not disable Keycloak-issued application tokens. Hide on login page = Off permits displaying the Entra login choice.

Security boundary: These flows are not themselves evidence of enterprise controls. To document their actual effect, inspect Authentication → Flows and identify which executions are enabled, required, conditional or disabled.

Important clarification: The two custom flows are especially important: they are the extension points for controlled user onboarding and post-authentication governance. The screenshot does not reveal their internal steps.

SAML NameFormat: a concrete matching example

The Attribute Name field tells Keycloak which claim to read (firstName). The Name Format field tells Keycloak how that claim name is represented in the SAML assertion. With ATTRIBUTE_FORMAT_BASIC, a compatible assertion attribute can look like this:

<saml:Attribute Name="firstName"
    NameFormat="urn:oasis:names:tc:SAML:2.0:attrname-format:basic">
    <saml:AttributeValue>Susan</saml:AttributeValue>
</saml:Attribute>

What Keycloak does: the mapper finds the incoming firstName claim using the matching name/format, reads its value, and stores it in the Keycloak user attribute firstName, subject to the mapper and sync behavior.

For contrast, Entra could emit NameFormat="urn:oasis:names:tc:SAML:2.0:attrname-format:uri" instead. That is a different naming format; the mapper needs to match the actual assertion configuration. The screenshot does not prove which format Entra sent.

First-name distinction: This imports profile data; it does not determine the NameID used for external account identification.

Important clarification: Verify the SAML assertion actually includes firstName in the expected name format; otherwise the mapper will not populate the value.

End-to-end relationship

Microsoft Entra ID authenticates a user and produces a SAML response. Keycloak receives that response at its broker endpoint, checks the trusted IdP and applicable security conditions, identifies or provisions the local user, and imports configured claims. Imported entraRoles values do not by themselves authorize a user to perform privileged operations.

Before deploying: verify Entra issuer and metadata, Keycloak ACS and entity ID alignment, signing certificates and signature verification, NameID consistency, attribute naming, first-login account linking, least-privilege authorization, and logout behavior.
