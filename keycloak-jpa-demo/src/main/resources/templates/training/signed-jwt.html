Concept

What Problem Are We Solving?

A traditional confidential OAuth client proves its identity using a reusable shared secret. Signed JWT changes that trust model: the application proves possession of a private key without transmitting that private key to Keycloak.

Traditional Model
SHARED CREDENTIAL

Both the application and authorization server depend on a reusable secret value.

Trust Model

The Key Idea: Asymmetric Cryptography

The private and public keys are mathematically related but serve completely different purposes. The application signs. Keycloak verifies.

JWT Internals

Anatomy of the Client Assertion

The assertion uses the familiar three-part JWT structure: Header, Payload and Signature.

01 — HEADER 
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "client-key-1"
}

Identifies the signing algorithm and may identify the signing key.

02 — PAYLOAD 
{
  "iss": "supplier-service",
  "sub": "supplier-service",
  "aud": ".../token",
  "exp": 1789991060,
  "jti": "..."
}

Identifies the client and constrains where and when the assertion can be accepted.

03 — SIGNATURE 
RSASHA256(
  base64Url(header)
  + "."
  + base64Url(payload),
  privateKey
)

Provides cryptographic proof that the caller possesses the private signing key.

HEADER . PAYLOAD . SIGNATURE

Comparison

Client Secret vs. private_key_jwt

Both approaches authenticate a confidential client, but the credential model and operational responsibilities are different.

Critical Distinction

Do Not Confuse the Two JWTs

The client assertion and the access token can both be JWTs, but they have different creators, recipients and purposes.

Key Takeaway

Authentication Through Cryptographic Proof

With private_key_jwt, the client authenticates by demonstrating possession of its private signing key.

The application creates a short-lived JWT assertion and signs it locally. Keycloak uses the corresponding public key to verify the signature and validates the assertion claims before processing the OAuth token request.
