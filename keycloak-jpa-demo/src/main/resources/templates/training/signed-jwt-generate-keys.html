Generating Keys Inside Keycloak

A private_key_jwt client needs asymmetric cryptographic material: the client signs an assertion with a private key and Keycloak verifies that signature with the corresponding public key.

Instead of generating the keypair externally with keytool or OpenSSL and importing it, this lab lets Keycloak generate the material and provides the client-side key material as a password-protected PKCS12 archive.

First Principle

Why Does private_key_jwt Need a Keypair?

With ordinary client-secret authentication, both parties know the same secret. With private_key_jwt, the cryptographic responsibilities are separated. The OAuth client possesses private signing material while Keycloak verifies the resulting digital signature using the corresponding public material.

Public verification material does not need the same secrecy as the private key.

Lab-Specific Finding

Why Did This POC Generate Keys Inside Keycloak?

Observed in This Lab

External PKCS12 Import Hit a Parsing Problem

The original lab found that externally created PKCS12 material produced through either keytool or OpenSSL encountered a parsing problem on this environment's import path.

Generating the material inside Keycloak avoided that specific path because Keycloak was working with material produced through its own generation workflow.

Important Distinction

This lab result does not mean external key generation is conceptually invalid.

It explains why this particular POC chose the Keycloak-generated path.
Key Generation Deep Dive

Questions to Understand Before Moving On

The workflow creates asymmetric cryptographic material for the client authentication use case. The private half is used for signing while the corresponding public material is used for verification.

Asymmetric Keypair

Not exactly. PKCS12 is a container format. The archive can contain a private-key entry together with associated certificate material and can hold multiple alias-based entries.

When the client later submits a signed JWT client assertion, Keycloak needs trusted public verification material corresponding to the client's signing key so it can validate the digital signature.

The asymmetric model separates the two operations. 
Private Key
    → Sign

Public Key
    → Verify

That separation is the foundation of this client-authentication approach.

The password protects access to the keystore contents. In production, both the archive and its unlocking credential should be handled according to the deployment's key/secrets-management controls.

PKCS12 is standardized and broadly interoperable beyond the Java ecosystem. Modern Java also uses PKCS12 as its default keystore type.

Key replacement requires coordinating the client's signing material with the verification material trusted by Keycloak.

In an enterprise deployment, that process should be treated as credential/key lifecycle management rather than as a one-time setup exercise.

1 — Cryptographic Primitive

RSA and RS256

RSA is an asymmetric public-key algorithm: the private key performs the signing operation while the corresponding public key verifies the result. RS256 is the JOSE algorithm identifier for an RSA signature using SHA-256. That is exactly what JWSAlgorithm.RS256 selects in the Java class.

Private Key

Sensitive material retained by the client. In this POC it is retrieved from PKCS12 and passed to the Nimbus RSA signer.

PrivateKey privateKey =
 (PrivateKey) keyStore.getKey(
   keyAlias, password);

Public Key

Non-secret verification material. Keycloak can verify a signature without obtaining the client's private key.

PRIVATE KEY → SIGN
PUBLIC KEY  → VERIFY

2 — Trust Framework

PKI, Certificate Authorities and X.509

Public Key Infrastructure (PKI) is the wider trust framework for public/private keys and digital certificates. A Certificate Authority (CA) issues and digitally signs certificates. An X.509 certificate is a standardized structure that binds a subject identity to public-key material and includes information such as issuer, serial number and validity period.

3 — Storage Vocabulary

Keystore vs. Truststore

The names describe two different security responsibilities. A keystore answers, “What private identity/signing material do I possess?” A truststore answers, “Which certificates or issuing authorities do I trust?” Both can use PKCS12 as the physical container format.

4 — Tooling

keytool and OpenSSL

keytool and OpenSSL are tools, not trust models. They create, inspect, convert and manage the keys, certificates and stores used by RSA, X.509, PKI, TLS and Java.

keytool ships with the JDK and is especially convenient for Java keystores/truststores and PKCS12.

# Inspect PKCS12
keytool -list -v   -keystore signed-jwt-client-keystore.p12   -storetype PKCS12

# Import a trusted CA certificate
keytool -importcert   -alias jpa-demo-lab-ca   -file ca-cert.pem   -keystore truststore.p12   -storetype PKCS12

OpenSSL is a broad cryptography and TLS toolkit. The mTLS lab uses it to generate RSA keys, certificate signing requests, certificates and a PKCS12 archive.

openssl genrsa -out client-key.pem 2048

openssl req -new   -key client-key.pem   -out client.csr   -subj "/CN=x509-cert-client"

openssl pkcs12 -export   -inkey client-key.pem   -in client-cert.pem   -name x509-cert-client   -out client-keystore.p12

RSA/X.509/PKI describe algorithms, formats and trust concepts. Keystore/truststore describe storage roles. PKCS12 is a container format. keytool/OpenSSL are utilities that operate on the artifacts.

6 — Complete Source

SignedJwtAssertionGenerator

After the dependency walkthrough, the complete class can now be read naturally from imports to serialization.

package com.rollingstone.demo.service;

import com.nimbusds.jose.JWSAlgorithm;
import com.nimbusds.jose.JWSHeader;
import com.nimbusds.jose.crypto.RSASSASigner;
import com.nimbusds.jwt.JWTClaimsSet;
import com.nimbusds.jwt.SignedJWT;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.io.FileInputStream;
import java.security.KeyStore;
import java.security.PrivateKey;
import java.util.Date;
import java.util.UUID;

@Component
public class SignedJwtAssertionGenerator {

    private final String clientId;
    private final String audience;
    private final String keystorePath;
    private final String keystorePassword;
    private final String keyAlias;

    public SignedJwtAssertionGenerator(
            @Value("${signed-jwt.client-id}") String clientId,
            @Value("${signed-jwt.audience:${signed-jwt.token-endpoint}}") String audience,
            @Value("${signed-jwt.keystore-path}") String keystorePath,
            @Value("${signed-jwt.keystore-password}") String keystorePassword,
            @Value("${signed-jwt.key-alias}") String keyAlias) {
        this.clientId = clientId;
        this.audience = audience;
        this.keystorePath = keystorePath;
        this.keystorePassword = keystorePassword;
        this.keyAlias = keyAlias;
    }

    public String generateSignedAssertion() throws Exception {
        KeyStore keyStore = KeyStore.getInstance("PKCS12");

        try (FileInputStream fis = new FileInputStream(keystorePath)) {
            keyStore.load(fis, keystorePassword.toCharArray());
        }

        PrivateKey privateKey = (PrivateKey) keyStore.getKey(
                keyAlias, keystorePassword.toCharArray());

        if (privateKey == null) {
            throw new IllegalStateException(
                    "No private key found under alias '"
                    + keyAlias + "' in " + keystorePath);
        }

        Date now = new Date();
        Date expiry = new Date(now.getTime() + 60_000L);

        JWTClaimsSet claims = new JWTClaimsSet.Builder()
                .issuer(clientId)
                .subject(clientId)
                .audience(audience)
                .expirationTime(expiry)
                .issueTime(now)
                .jwtID(UUID.randomUUID().toString())
                .build();

        SignedJWT signedJWT = new SignedJWT(
                new JWSHeader(JWSAlgorithm.RS256),
                claims);

        signedJWT.sign(new RSASSASigner(privateKey));

        return signedJWT.serialize();
    }
}

8 — Critical Distinction

private_key_jwt vs. X.509 mTLS

Both use asymmetric cryptography and may involve certificates, but they prove client identity at different protocol layers.

Key Takeaway

Key Generation Establishes the Cryptographic Trust Relationship

The private key signs. The public material verifies.

The PKCS12 archive gives the client access to its sensitive signing material. Keycloak is configured with the corresponding verification material. Later, the client proves possession of its private key by creating a signed JWT assertion rather than transmitting the private key itself.
