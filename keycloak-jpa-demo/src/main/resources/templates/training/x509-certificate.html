The client proves possession of the certificate's private key during the TLS handshake. Keycloak can then authenticate the client using the presented X.509 certificate and configured certificate identity rules.

Concept

What Problem Are We Solving?

Machine-to-machine OAuth clients need a way to prove who they are before an authorization server issues tokens. X.509 client authentication moves that proof into a mature certificate-based trust model.

Foundation

TLS vs. Mutual TLS

Normal HTTPS typically authenticates the server to the client. Mutual TLS adds authentication in the opposite direction: the server also requests and validates a client certificate.

Capability Normal TLS / HTTPS Mutual TLS
Server presents certificate Yes Yes
Client validates server Yes Yes
Client presents certificate Usually no Yes
Server validates client Not at TLS certificate layer Yes
Result Server-authenticated encrypted channel Mutually authenticated encrypted channel

End-to-End Protocol

What Happens During X.509 Client Authentication?

There are two important layers to understand: first the TLS connection establishes certificate-based trust; then the OAuth token request is processed over that authenticated connection.

The Spring Boot service or another machine client opens a TLS connection to the Keycloak token endpoint.

The client validates the server certificate using its trusted CA store, just as it would during a normal HTTPS connection.

In mutual TLS, the server side also requests certificate credentials from the connecting client.

Subject DN Matching

Receiving a trusted certificate is only part of the problem. Keycloak must determine whether that certificate represents the OAuth client attempting to authenticate.

Certificate

Example Subject DN 

CN=supplier-service,
OU=Applications,
O=Example Corp,
C=US

The Subject Distinguished Name contains identity attributes describing the certificate holder.

Keycloak

Subject DN Rule 

CN=supplier-service,
OU=Applications,
O=Example Corp.*

The configured matching rule determines whether the presented certificate belongs to the expected OAuth client.

Enterprise Operations

Certificate Lifecycle Matters

X.509 removes dependency on a conventional OAuth client secret, but it does not remove credential lifecycle management. Certificates and their private keys must still be governed.

Issue

Create the key pair and obtain a certificate from an approved CA.

Protect

Store the private key in an appropriately protected secret store, keystore or hardware-backed system.

Renew

Replace certificates before expiration and plan for controlled key rotation.

Revoke

Compromised or retired credentials must no longer be accepted.

Revocation

What If a Certificate Is Compromised?

Expiration is not enough. An enterprise may need a way to stop trusting a certificate before its normal expiration date.

CRL

Certificate Revocation List

A CA can publish a list of certificates that have been revoked before their expiration dates.

Certificate validation infrastructure can consult that revocation information when deciding whether a presented certificate remains trustworthy.

OCSP

Online Certificate Status Protocol

OCSP provides a mechanism for obtaining status information about a particular certificate.

The broader PKI architecture determines how revocation status is obtained and enforced.

Troubleshooting

When Authentication Fails, Check the Layers in Order

X.509 authentication crosses several architectural boundaries. Debugging is easier when TLS, PKI, certificate identity and OAuth are treated as separate layers.

First determine whether the client can establish the TLS connection at all. Certificate authentication cannot reach the Keycloak client-authentication stage if TLS negotiation fails first.

Verify that the client is configured with the intended certificate and private key and that the TLS endpoint requests a client certificate.

A certificate and an unrelated private key cannot successfully establish proof of possession. Confirm that the configured certificate and private key form the intended pair.

Check the certificate chain, issuing CA, intermediate certificates and the trust configuration at the TLS termination point.

Inspect the certificate's Not Before and Not After values. Also verify system clocks when validity errors appear unexpectedly.

A cryptographically valid certificate can still fail client authentication if its identity does not match the rule configured for the Keycloak client.

If a reverse proxy, ingress controller or load balancer terminates TLS before Keycloak, determine where client certificate validation occurs and how trusted certificate identity information reaches Keycloak.
Architecture Perspective

Where X.509 Fits Well

Certificate-based client authentication is especially natural in environments that already operate certificate issuance, rotation and trust infrastructure.

Service Platforms

Internal service environments where certificates are already part of workload identity.

Service Mesh

Platforms that already establish authenticated service-to-service TLS connections.

Enterprise PKI

Organizations with established CA, issuance, revocation and certificate lifecycle processes.

B2B Integration

Controlled machine-to-machine integrations where certificate trust already forms part of the security architecture.

Key Takeaway

The Certificate Establishes Client Identity

X.509 client authentication combines TLS, asymmetric cryptography, certificate trust and OAuth client authentication.

The client keeps possession of its private key, presents its X.509 certificate and proves possession of the corresponding private key through the TLS protocol. Keycloak can then use the trusted certificate identity to authenticate the OAuth client before issuing an access token.
