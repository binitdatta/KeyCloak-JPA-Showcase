Core Mental Model

First Question: Where Is the Foreign Key?

Before looking at @OneToOne, @OneToMany or @ManyToMany, inspect the database. The physical foreign-key structure tells us how the relationship is persisted.

Practical modeling rule
When the relationship needs business attributes of its own, model the join as an entity rather than hiding it behind a raw @ManyToMany.

JPA Vocabulary

Owning Side vs. Inverse Side

This terminology often causes confusion because "owner" does not mean business ownership. It describes which side controls persistence of the relationship mapping.

Owning Side

Defines the Relationship Mapping

In the foreign-key examples in this POC, the owning entity is the entity mapped to the table that stores the FK. 

@JoinColumn(name = "customer_id")

For the Product ↔ Tag relationship, Product defines the join table with @JoinTable.

Inverse Side

Uses mappedBy

The inverse side points back to the field that defines the mapping. 

@OneToMany(mappedBy = "customer")

@OneToOne(mappedBy = "customer")

@ManyToMany(mappedBy = "tags")
Common Source of Confusion

What Does mappedBy Actually Point To?

Order.java 
@ManyToOne
@JoinColumn(name = "customer_id")
private Customer customer;
Customer.java 
@OneToMany(mappedBy = "customer")
private List<Order> orders;
Important: mappedBy = "customer" refers to the Java field name customer inside Order. It does not refer to the SQL column name customer_id.

Relationship Deep Dive

JPA Relationship Questions

The decisive database characteristic is the uniqueness of customer_profiles.customer_id. 
customer_profiles.customer_id
    FOREIGN KEY
    UNIQUE

Without that uniqueness constraint, multiple profile rows could reference the same customer, which would no longer represent the intended one-to-one relationship.

The orders table stores customer_id. Therefore the Order entity defines the foreign-key mapping: 
@ManyToOne
@JoinColumn(name = "customer_id")
private Customer customer;

It points to the Java field named customer on the other entity. 
Order.java

private Customer customer;


Customer.java

@OneToMany(mappedBy = "customer")

It is not the database column name.

A product can reference many tags and a tag can reference many products. Neither table can represent that relationship with one simple foreign-key column.

The intermediate table stores each pairing: 

product_tags

product_id | tag_id
-----------+-------
101        | 1
101        | 3
102        | 1

Because the Order/Product pairing has data of its own: 
quantity
unit_price_at_purchase

That relationship therefore becomes a first-class domain object: OrderItem.

This is an important domain-modeling consequence of making OrderItem an entity.

A product's current price can change after an order is placed. The line item can preserve the price associated with that transaction rather than depending on the product's later price. 

Product.price
    = current product price

OrderItem.unit_price_at_purchase
    = transaction-time price

The source deliberately maps Product ↔ Tag using a Set<Tag>. A Set naturally models unique membership: a product either has a tag or it does not.

It also avoids representing duplicate tag membership in the Java collection.

Troubleshooting

Common Relationship Mapping Problems

Remember that mappedBy refers to a Java property on the owning entity. 
// Order.java
private Customer customer;

// Customer.java
@OneToMany(mappedBy = "customer")

For the bidirectional relationships demonstrated here, one side defines the relationship using @JoinColumn or @JoinTable; the inverse side uses mappedBy.

Inspect the database constraint. The relationship shown in this POC depends on the FK being unique: 
customer_id UNIQUE

If a join suddenly needs fields such as quantity, purchase price or other relationship-specific attributes, reconsider whether it should remain a raw many-to-many mapping.

OrderItem demonstrates the association-entity approach.

Key Takeaway

Start with the Database Relationship

Do not memorize JPA annotations in isolation.

Look at the tables. Find the foreign key. Determine whether it is unique. Look for a join table and ask whether that relationship has attributes of its own. Then translate that relational structure into @OneToOne, @ManyToOne, @OneToMany, @ManyToMany, or an association entity. In the bidirectional examples in this application, the side defining @JoinColumn or @JoinTable is the owning side, while the inverse side uses mappedBy.
