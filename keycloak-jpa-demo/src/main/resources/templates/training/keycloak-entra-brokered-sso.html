01 · Architecture blueprint

Five participants in an enterprise federation

The web browser moves between Spring Boot, Keycloak, and Microsoft Entra ID. The Spring application does not process the SAML assertion: Keycloak does. After federation, Spring Security receives an OIDC authorization code and completes its standard OIDC login.

Browser / employee

Spring Boot + Security

Keycloak 26

Two data stores

02 · Browser and protocol journey

Every handoff, numbered

The numbering below aligns with the architecture image. A redirect or HTML form is returned to the browser; the browser makes the next HTTP request. These are not all direct back-end service calls.

1
Application HTTP

Browser requests a protected page

The employee navigates to a secured Spring Boot URL such as /dashboard. Spring Security finds there is no authenticated local session.

2
OIDC authorization

Spring Security redirects the browser to Keycloak

Spring Security's oauth2Login() begins Authorization Code flow, sending the browser to Keycloak's OIDC authorization endpoint with client ID, redirect URI, scopes, state and any applicable PKCE parameters.

3
Keycloak login screen

Keycloak offers Microsoft Entra ID as an identity provider

Keycloak renders the login page. The Entra identity-provider button is made available through the realm's identity-broker configuration.

4
Start SAML federation

User selects the Entra login option

Keycloak initiates SAML brokering and prepares an AuthnRequest for Entra ID. The browser is the intermediary for the outward request.

5
SAML AuthnRequest → browser → Entra

Browser delivers the SAML authentication request

Keycloak returns a browser redirect or form depending on SAML binding. The browser then requests the Entra SSO endpoint, carrying SAMLRequest and correlation state as applicable. It is not simply a direct Keycloak-to-Entra API invocation.

6
Authentication + MFA

Entra authenticates the employee

Entra applies its sign-in, MFA and Conditional Access policies. After success it constructs the SAML response/assertion for the configured Keycloak service provider.

7
Entra → browser → Keycloak ACS

Browser POSTs Entra's SAMLResponse to Keycloak

Entra sends HTML containing a form with a Base64-encoded SAMLResponse (and usually RelayState). JavaScript or the user submits that form via HTTP POST from the browser to Keycloak's broker endpoint, such as /realms/{realm}/broker/{alias}/endpoint.

8
Keycloak validation and federation

Keycloak verifies the assertion and resolves federated identity

Keycloak validates the SAML response according to configuration—issuer, destination, signature, recipient, audience, timing and correlation—and extracts NameID and mapped attributes. It looks up or establishes the federated identity link and local Keycloak user as required. Actual database rows depend on the first-broker flow and existing-account state.

9
Custom Java · first-time branch

First Broker Login / Create User If Unique

When Keycloak regards this as a new external identity, its configured First Broker Login flow can invoke your Java authenticator. Your custom implementation validates claims and, if the application user is absent, calls your application service or DAO to create the MySQL user. Keycloak's own linked-user persistence and the application database write are distinct operations.

10
Custom Java · subsequent-login branch

Post Login flow updates the application user

For returning brokered users, your configured Post Login flow can invoke a custom authenticator to compare Entra-sourced attributes, roles and groups and update application MySQL records. Whether it also executes during first login depends on your actual authentication-flow configuration.

11
OIDC code + token exchange

Keycloak completes OIDC back to Spring Security

Keycloak redirects the browser to the Spring Security OAuth2 callback with an authorization code. Spring Security then makes a server-to-server token request to Keycloak, validating the ID token and establishing authentication. The browser is not the party that exchanges the code for tokens in this server-side web-app pattern.

12
Application response

Spring Boot returns the secured page

Spring Security creates or uses the local authenticated session and the browser receives the requested page, subject to application authorization checks.

Core separation: Spring Boot ↔ Keycloak is OIDC. Keycloak ↔ Entra is SAML 2.0 with browser relay. Keycloak ↔ Application MySQL is your custom provisioning/synchronization integration, not a built-in SAML database-writing behavior.
03 · Identity lifecycle

What changes between the first and later logins?

First broker login

  1. Entra proves user identity and sends assertions.
  2. Keycloak validates and extracts identity claims.
  3. Keycloak invokes its configured first-broker flow for a previously unlinked identity.
  4. The custom Create User If Unique authenticator checks data quality and duplicate risk.
  5. The custom application integration creates the corresponding MySQL user when needed.
  6. Keycloak completes account linking/federated identity persistence if the flow succeeds.

Returning user

  1. Entra authenticates the employee again.
  2. Keycloak resolves the previously linked federated identity.
  3. The configured custom Post Login authenticator evaluates current attributes.
  4. Changed profile attributes and approved application roles/groups are reconciled in MySQL.
  5. Keycloak completes OIDC and Spring Boot opens the protected page.
Important: First-login and post-login flows are configurable Keycloak authentication-flow hooks, not an automatic guaranteed sequence for every deployment. They do not imply an atomic distributed transaction between Keycloak's database and MySQL. Use idempotency, retries and reconciliation for failure handling.
04 · Custom Java extension responsibility

What the two custom authenticators should do

ResponsibilityFirst Broker LoginPost Login
Entry pointNew/unlinked brokered identityConfigured after successful external authentication
InputsVerified brokered identity, validated/mapped claimsKnown federated user and current mapped identity claims
ValidationRequired identity fields, uniqueness, policy eligibilityAttribute integrity, account state, role/group mapping policies
Application MySQLIdempotent user creation, if absentUpdate changed attributes, roles and groups
Failure behaviorDeny or handle provisioning failure according to policy; audit resultDecide fail-closed vs allowed limited access; audit and retry safely
Keycloak own DBKeycloak owns local identities and federation linksKeycloak manages its own user and brokered session lifecycle

In Keycloak 26, custom authentication logic is typically packaged as a Java provider using the Keycloak Authentication SPI (for example, Authenticator and AuthenticatorFactory), registered as a provider JAR and configured into the relevant flow. The application database integration is your custom code, not a default Keycloak feature.

Entra issues signed SAML identity attributes. Keycloak validates the assertion and then maps selected claims to brokered identity/user attributes. A claim named roles or groups does not by itself grant a Keycloak role or application permission. Your custom mapping, authorization policy, and application role-assignment logic must explicitly define what those values mean.

Keycloak is the IAM system for authentication sessions, linked identities and realm-level policy. Your application's MySQL database stores domain-specific entities, user entitlements, business role relationships and lifecycle data. This makes application authorization explicit and prevents coupling business entities directly to Keycloak's internal database schema.

After successful brokering, Keycloak—not Entra—issues the OIDC tokens for the Spring Boot OIDC client. Spring Security validates the OIDC authentication result and stores the application security context in the server-side web session. The app can enforce its own authorization against application user and entitlement records.
05 · Production safeguards

Security and governance checks your viewers should recognize

SAML boundary

  • Validate trust in Entra signing certificates and signatures.
  • Check assertion audience, destination, recipient and validity window.
  • Correlate responses and prevent replay; require secure HTTPS in deployed environments.
  • Keep SAMLResponse, cookies, session identifiers and tokens out of public logs.

Identity and application boundary

  • Prevent duplicate identities and unsafe email-only account linking.
  • Apply least-privilege mappings and explicit role/group entitlement rules.
  • Audit failed provisioning; design idempotent MySQL updates and reconciliation.
  • Decide how disabled users, offboarding and stale sessions are handled.
This course demonstrates a production-inspired design. The diagram alone does not establish that all security controls or application database behaviors have been implemented. Verify them in configuration, custom Java source, and actual network/log evidence.
