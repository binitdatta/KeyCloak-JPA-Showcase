Foundation

What Is First Broker Login?

Identity brokering allows Keycloak to delegate authentication to another Identity Provider. On the user's first successful brokered authentication, Keycloak must decide how that external identity should relate to a user in the local Keycloak realm.

Step 1

External Authentication

The user authenticates through the external Identity Provider configured as a broker in Keycloak.

Step 2

First Broker Login

Keycloak runs its First Broker Login authentication flow to determine how to handle the external identity.

Step 3

Link or Create

Depending on the flow outcome, Keycloak can associate the brokered identity with a local user or create the appropriate local user.

Enterprise Requirement

The Built-In Collision Check Is Not Enough for Our POC

Keycloak's existing Create User If Unique behavior protects against username and email collisions. Our migration scenario introduces another question: does this identity actually exist and validate in the enterprise system of record?

Question Built-In Create User If Unique Our Extended Authenticator
Is username unique? Checked Preserved through superclass behavior
Is email unique? Checked Preserved through superclass behavior
Does identity exist in external source? Not part of this POC's built-in check Calls /api/auth/validate
Can external roles/groups be captured? Not part of this custom requirement Stores authentication-session notes
Prevent orphaned migrated user? No external validation 401 fails the flow
Design Principle

Extend the Built-In Behavior — Don't Reimplement It

The custom provider does not attempt to reproduce Keycloak's existing Create User If Unique logic. It subclasses that authenticator, performs the additional enterprise validation, and then delegates back to the superclass.

Migration Pattern

Why This Matters During Identity Migration

Legacy Identity Source

Existing customer identities may still live in a legacy database or another enterprise system while Keycloak becomes the new identity layer.

Controlled Transition

The external system can participate in the decision before a corresponding local Keycloak identity is created.

Validated Provisioning

A successfully authenticated external user does not automatically become a migrated local user; the enterprise validation step must also succeed.

Enterprise Design Considerations

The External Validation API Becomes Part of Authentication

Once the authentication provider depends on an external validation endpoint, that dependency becomes part of the login path. It should therefore be treated as identity infrastructure, not as an ordinary convenience API.

Secure the API

Protect the validation service and define which trusted component is permitted to invoke it.

Control Latency

A slow validation dependency can directly extend the time required to complete the first login.

Define Failure Behavior

Distinguish an invalid identity from technical failure of the external system.

Audit Decisions

Authentication, validation and provisioning decisions should be observable without logging unnecessary sensitive identity data.

Key Takeaway

Extend → Validate → Preserve Context → Delegate

The POC adds an enterprise identity check without throwing away Keycloak's existing First Broker Login behavior.

ExtendedCreateUserIfUniqueAuthenticator validates the incoming brokered identity against /api/auth/validate. A successful result allows roles and groups to be stored as havi.externalRoles and havi.externalGroups, after which the authenticator delegates back to super.authenticateImpl(). A rejected identity fails the flow instead of creating an orphaned local account. The next Post-Login Flow can then consume the state preserved during this stage.
