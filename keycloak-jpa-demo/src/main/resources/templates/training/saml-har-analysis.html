1. System architecture & browser-mediated SAML flow

The browser is a first-class participant. Spring Boot uses Spring Security to begin an OpenID Connect authorization-code login with Keycloak. Keycloak then acts as an intermediary SAML Service Provider toward Entra ID. In an HTTP-POST SAML response flow, Entra returns an HTML form to the browser; the browser posts SAMLResponse to Keycloak’s Assertion Consumer Service. This is a reference flow illustrated by the diagram—not a packet-by-packet reconstruction from this HAR.

Roles in this configuration: Spring Boot is the OAuth2/OIDC client to Keycloak; Keycloak is OIDC provider to Spring Boot and SAML Service Provider / broker toward Entra; Entra is the external SAML Identity Provider. Do not treat the Spring Boot application as a direct SAML SP unless you have separately configured Spring Security SAML.

4. Detailed SSO exchange — conceptual protocol walkthrough

These steps explain the normal integration represented in your architecture image. Labels identify what the provided HAR does and does not show. The important SAML relay is explicitly Keycloak → Browser → Entra → Browser → Keycloak.

The application encounters an unauthenticated request and Spring Security initiates sign-in.

Expected; not captured

Spring Security uses authorization code flow to authenticate through Keycloak. HAR page-title metadata shows the Keycloak authorization URL.

Page title supported; redirect not captured

Keycloak operates as a SAML Service Provider to Entra. Typically the browser carries an HTTP-Redirect or POST binding request.

Expected; payload not captured

The browser loads Microsoft sign-in resources. The HAR directly records CDN image/animation GET requests.

Static resources captured

Following successful authentication, Entra may return an HTML page with hidden SAMLResponse and RelayState fields; browser auto-submits it.

Expected; response form not captured

The browser submits the SAML response to Keycloak’s /broker/entra-saml/endpoint. Keycloak validates issuer, signatures, conditions, destination and audience before identity import/linking.

Expected; POST not captured

Keycloak’s first-broker-login flow can link or create a local user subject to configuration. HAR cannot establish whether creation occurred.

Not captured

Once broker sign-in completes, Keycloak resumes the original OIDC flow and browser returns to Spring Security callback with authorization code.

Expected; callback not captured

Spring Security backend exchanges authorization code for tokens and creates the application security context/session.

Expected; token request not captured

App logout, Keycloak session logout, and Entra session logout are distinct; SAML SLO and OIDC RP-initiated logout require separate verification.

Not captured
Why there are two protocols: Spring Security’s visible OAuth2 callback route (/login/oauth2/code/keycloak) is an OIDC application login, while the Keycloak-to-Entra leg uses SAML 2.0. Keycloak bridges the two. The browser carries the SAML message through front-channel protocol bindings; it does not validate signatures—that responsibility belongs to Keycloak.

4A. SAML wire-format examples — XML request, XML response and browser HTML

These examples show the message structures behind the numbered architecture diagram. The browser is a carrier of SAML messages; it does not verify the SAML assertion. The HTML sample contains a Base64-encoded copy of the same sample XML response displayed in the second tab.

6. How to capture a complete trace for training

  1. Open Chrome DevTools → Network before beginning sign-in.
  2. Enable Preserve log and optionally Disable cache.
  3. Start at a protected Spring Boot page in a private browser session.
  4. Complete the login, including Entra authentication and any MFA challenge, then return to the app.
  5. Run logout as a separate clearly marked segment and observe browser navigation to Keycloak/Entra logout endpoints.
  6. Export HAR and remove secrets before sharing: cookies, authorization codes, tokens, full SAMLRequest/SAMLResponse values, credentials, user identities, tenant/client IDs and sensitive attributes.
Security reminder: HARs may contain active session material even when URLs look innocuous. For public YouTube material, replace sensitive values with synthetic examples and keep an unredacted original only in a secure private location.
