Flow Ordering

Why Provisioning Happens in a Separate Step

The first custom authenticator performs validation while Keycloak is still deciding whether and how the brokered user should be created. Role and group provisioning belongs later, when the user object is available.

Stage Primary Responsibility UserModel Action
Extended Create User If Unique Validate brokered identity against external source May not yet be available for provisioning Preserve roles/groups as session notes
Keycloak User Creation Create/resolve local brokered user Created/resolved Establish local identity
PostLoginRoleGroupAuthenticator Provision authorization data Available Grant roles and join groups
Separation of Responsibilities

Two Authenticators — Two Different Jobs

Earlier Step

ExtendedCreateUserIfUniqueAuthenticator

  • Receives the brokered identity.
  • Calls the external validation service.
  • Rejects an invalid external identity.
  • Captures external roles.
  • Captures external groups.
  • Stores those values as authentication-session notes.
Later Step

PostLoginRoleGroupAuthenticator

  • Runs after the user exists.
  • Reads external role/group notes.
  • Resolves names against the realm.
  • Calls user.grantRole(...).
  • Calls user.joinGroup(...).
  • Calls context.success() so a provisioning miss does not block login.
State Handoff

The two authenticators do not need to be tightly coupled. Episode F2 writes temporary authentication state; Episode F3 consumes it after user creation.

Important Distinction

REQUIRED Execution — But Provisioning Misses Do Not Block Login

These are two different decisions. The execution is configured as Required, meaning Keycloak runs the authenticator as part of the flow. Inside the authenticator, however, this POC logs provisioning misses and still calls context.success().

Flow Requirement

REQUIRED

The provisioning execution is part of the configured First Broker Login flow and is expected to execute.

Provisioning Behavior

Missing Entitlement vs. Failed Authentication

The original implementation deliberately treats provisioning misses differently from identity validation failures. The earlier authenticator can reject an invalid identity; this later authenticator logs a provisioning warning and allows the login to continue.

Condition Stage Behavior in This POC Login
External identity invalid First Broker Login validation Authentication flow fails Blocked
Role cannot be provisioned Post-login provisioning Warning logged Continues
Group cannot be provisioned Post-login provisioning Warning logged Continues
All assignments succeed Post-login provisioning Roles/groups applied Continues

Verify the expected group: 
/customers/migrated

exists and can be resolved before user.joinGroup(...) is invoked.

The reason this logic is placed later in the flow is precisely so provisioning occurs after the local brokered user exists.

Verify execution ordering if the authenticator cannot obtain the expected user.

Verify that the provider appears in the flow configuration and that the registered provider ID is: 
havi-post-login-role-group

Because provisioning misses do not block login in this implementation, a successful login does not by itself prove that every requested entitlement was provisioned.
Inspect the provider logs when the user logs in successfully but an expected role or group is missing.

Architectural Pattern

Authentication Establishes Identity. Provisioning Establishes Access.

This POC deliberately separates identity validation from authorization provisioning. That separation makes the broker flow easier to reason about: first establish that the identity is valid, then create the user, then provision the access information associated with that identity.

Key Takeaway

Validate → Create → Provision → Continue

Episodes F2 and F3 together turn first broker login into a complete onboarding pipeline.

The first custom authenticator validates the incoming identity and preserves external roles and groups. Keycloak then creates the local user. The PostLoginRoleGroupAuthenticator executes after the user exists, resolves the requested realm roles and groups, calls user.grantRole(...) and user.joinGroup(...), and completes with context.success(). The result is automated onboarding without a separate after-the-fact provisioning script.
