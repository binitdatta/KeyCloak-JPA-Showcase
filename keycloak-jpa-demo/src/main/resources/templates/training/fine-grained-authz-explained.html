EPISODE D2 · CONCEPTS · SCREEN-BY-SCREEN

Fine-Grained Authorization, ExplainedEvery tab, every field, on the real admin console.

Keycloak's Authorization Services let a resource server say "yes" or "no" per action, per client — not just "is this token valid," but "is this client allowed to do this specific thing to this specific resource." This page walks the capability-demo-client → Authorization tab exactly as configured for the live demo.

Authorization → Settings
Import Bulk-loads an entire authorization configuration (resources, scopes, policies, permissions) from a JSON file — the same shape the Export tab produces. Useful for moving this setup between realms or environments.
Policy enforcement mode Enforcing (used here): a request is denied unless an explicit Permission grants it. Permissive: requests are allowed even with no matching permission — decisions are still computed and logged, just not enforced. Disabled: authorization services are switched off for this client entirely.
Decision strategy How this client's overall authorization decision is reached when several permissions apply. Unanimous (used here): every applicable permission must vote Permit. Affirmative: one Permit vote is enough. This is the client-wide default; each individual Permission can override it with its own strategy (see Permissions tab below).
Remote resource management On (used here) lets a resource server register and manage resources dynamically at runtime via Keycloak's UMA Protection API, instead of only through this admin console. Not used by this lab's demo — resources are defined statically here — but left on since it's the client default.
Authorization → Resources

Two resources exist: the client's built-in Default Resource (matches everything, /*) and the one this episode actually uses, Order Resource.

Name The unique identifier used everywhere else — Policies, Permissions, and the permission=Order Resource#order:view parameter sent to Keycloak's token endpoint.
Display name Human-friendly label shown in the console UI only; has no effect on evaluation.
Type An arbitrary URN used to group resources of the same "shape" — urn:capability-demo-client:resources:order. A Permission can target a resource type instead of one named resource, so every future resource of that type automatically inherits the same policy without a new permission being created for each one.
Owner Which entity owns this resource — here, the client itself (capability-demo-client). UMA also supports user-owned resources, where an individual end user owns and can share access to their own data.
URIs /api/orders/* — descriptive metadata mapping this resource to real endpoint paths. It documents intent; Keycloak's Policy Enforcer (a servlet filter/adapter, not used by this lab's demo) is what would actually intercept matching HTTP requests and check them against this resource automatically.
Create permission Shortcut link that jumps straight to a pre-filled "Create permission" form scoped to this resource, skipping the separate Permissions tab.
Authorization → Scopes
Name The scope identifier — order:view, order:approve. This is the exact string that appears after the # in the permission=Order Resource#order:view request parameter, and inside the granted RPT's authorization.permissions[].scopes array.
Display name Left the same as Name here; purely cosmetic in the console.
Create permission Same shortcut as on Resources — pre-fills a new scope-based permission for this specific scope.
Authorization → Policies
Name Order Viewer Policy / Order Approver Policy — the rule's identifier, referenced by whichever Permission(s) use it.
Type Role for both — evaluates true if the requesting identity holds a given realm or client role (order-viewer / order-approver respectively). Keycloak also offers User, Group, Client, Time, JS, and Aggregated policy types for more complex conditions.
Dependent permission Reverse-reference showing which Permission consumes this Policy — confirms the wiring: Order Viewer Policy → View Orders Permission, Order Approver Policy → Approve Orders Permission.
Description Free-text note; not evaluated, documentation only.
Authorization → Permissions
Name View Orders Permission / Approve Orders Permission — the binding rule itself: this is what Keycloak's decision engine actually evaluates when a UMA ticket is requested.
Type Scope-Based for both — the permission applies to one resource plus one specific scope on it (Order Resource + order:view, and Order Resource + order:approve). Keycloak also supports Resource-Based permissions, which cover every scope on a resource at once.
Associated policy Which Policy (or policies) must pass for this permission to grant. Each permission here has exactly one: its own role policy. If more than one policy were attached, the permission's own Decision Strategy setting (Unanimous/Affirmative, defaulting from the Settings tab) would decide how their votes combine.
Description Free-text note; not evaluated.
Authorization → Evaluate

A built-in dry-run sandbox — runs the real decision engine without needing a live token request, so misconfiguration is caught here before it ever reaches application code.

Client Which client's authorization settings to simulate under — pinned to capability-demo-client here.
Users Optional: pick a real user to simulate as, and their actual role/group assignments are used automatically. Left empty for this test, since the real flow uses a service account, not a logged-in user.
Roles Manually hand-pick which roles to simulate holding — used instead of Users when testing a service-account scenario. Set to order-viewer only, matching capability-demo-client's actual service-account role assignment.
Apply to Resource Type When On, evaluation runs against every resource sharing a given Type (see Resources tab) rather than one named resource instance. Off here — this test targets the named Order Resource directly.
Resources and Scopes The specific resource/scope pairs to test in this run — queued here as Order Resource / order:view and Order Resource / order:approve, so one Evaluate click checks both outcomes at once.
Contextual Information Collapsible section for injecting extra request-context attributes (time, custom claims) that a Time or JS policy could condition on. Not needed for the Role policies used in this episode.
Authorization → Export

The full authorization configuration as JSON — policyEnforcementMode, allowRemoteResourceManagement, and the complete resources / policies / permissions arrays. This is exactly the file format the Import button on the Settings tab consumes, so this whole setup can be version-controlled and re-applied to another realm with one click.

What the live demo does with all of this

The live demo asks Keycloak's token endpoint directly for permission to use a scope, via the urn:ietf:params:oauth:grant-type:uma-ticket grant: 

POST /realms/jpa-demo-realm/protocol/openid-connect/token
grant_type=urn:ietf:params:oauth:grant-type:uma-ticket
client_id=capability-demo-client
client_secret=***
audience=capability-demo-client
permission=Order Resource#order:view

Keycloak evaluates every Permission that matches the requested resource/scope pair, using the requesting client's own service-account roles. If every required Policy votes yes, Keycloak issues a fresh access token — a Requesting Party Token (RPT) — whose authorization claim lists exactly which permissions were granted. If any required Policy votes no, Keycloak returns 403 Forbidden with {"error":"access_denied"} — no token at all. This is the identical decision logic the Evaluate tab runs in its sandbox, now proven over the network with real client credentials.
