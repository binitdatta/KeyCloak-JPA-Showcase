1. Two different flow stages are shown

Important terminology: the screenshots do not show a duplicated replacement for the built-in Browser flow. The first two screenshots show Keycloak's built-in browser flow. The last two show your rollingstone-entra-first-broker-login flow, which is a First Broker Login flow. They participate at different points in authentication.

Browser authentication flow

Determines how a browser-based client session can authenticate to the realm. It contains mechanisms such as Cookie, Kerberos, Identity Provider Redirector, Username/Password, Organization logic, and conditional OTP.

Question it answers: “How should this browser establish an authenticated Keycloak session?”

First Broker Login flow

Runs after an external Identity Provider such as Microsoft Entra ID has authenticated a user and Keycloak receives the brokered identity for the first time. It decides how that external identity becomes associated with a local Keycloak user.

Question it answers: “What should Keycloak do with this externally authenticated identity the first time it sees it?”

3. What REQUIRED, ALTERNATIVE, CONDITIONAL and DISABLED mean

REQUIRED

The execution must succeed when its containing flow is being executed. A failure normally prevents that path from completing successfully.

ALTERNATIVE

The execution is one possible way to satisfy its flow level. This is why Cookie and Forms can coexist as alternatives: a valid cookie may avoid the need to display the login form.

CONDITIONAL

A sub-flow becomes required only when its configured condition executions evaluate so that the conditional flow applies.

DISABLED

The execution or sub-flow remains defined but is not considered an active authentication path.

5. What your customization changes

Built-in Browser Flow

  • Runs to establish browser authentication.
  • Supports SSO Cookie, external IdP redirect, local username/password and conditional OTP.
  • Does not itself implement your Entra user-provisioning database synchronization.
  • Can lead the browser toward an external IdP such as Entra.

Your First Broker Login Flow

  • Runs in the broker lifecycle for a first-time external identity.
  • Starts from a user who has already authenticated at the external IdP.
  • Contains account creation/linking semantics.
  • Introduces rollingstone Entra Create User (Ext) as REQUIRED.
  • Your extension takes responsibility for creating/persisting the Entra-backed user and initial role/group state.
Architectural consequence of the screenshot: because Handle Existing Account is disabled, the normal existing-account linking branch shown beneath it is not active. That is consistent with a lab in which incoming Entra identities are expected to represent new users, but duplicate-email/account-linking behavior deserves explicit design before production use.

6. End-to-end runtime: where both flows fit

1 • CLIENTApplication sends browser to Keycloak.
2 • BROWSER FLOWKeycloak determines the authentication mechanism.
3 • ENTRA SAMLUser authenticates externally and SAML Response returns.
4 • FIRST BROKER LOGINFor a new broker identity, your custom first-login flow runs.
5 • SESSIONKeycloak completes authentication and returns to the client.

Example path for a new Entra user

  1. A browser reaches a Keycloak-protected application.
  2. The realm's Browser flow is entered.
  3. An Identity Provider path sends the user to Microsoft Entra ID.
  4. Entra authenticates the user and returns a SAML Response to Keycloak.
  5. Keycloak's broker processes the external identity and IdP mappers populate broker context.
  6. Because this is the first brokered login for that identity, rollingstone-entra-first-broker-login executes.
  7. Your REQUIRED rollingstone Entra Create User (Ext) execution creates/provisions the local Keycloak user as designed.
  8. After the first-login flow succeeds, Keycloak can establish its authenticated session and continue back to the requesting client.

7. Parent/child requirement behavior visible in the UI

Read the indentation. A child execution's “Required” label does not mean it always runs globally. It means it is required if its parent flow is actually entered. This matters in your screenshot: several REQUIRED children live beneath a parent branch that is itself DISABLED.

Disabled parent

If the parent sub-flow is disabled, its children do not become active merely because they individually display REQUIRED.

Conditional parent

The child requirements matter after the conditional sub-flow has been determined to apply.

Alternative parent/path

An alternative branch competes with sibling alternatives as a way to satisfy that level of the flow.

9. Executive summary

The Browser flow and First Broker Login flow are complementary, not competing flows. The Browser flow decides how the browser authenticates. If that authentication is brokered to Entra, Entra authenticates the person and Keycloak receives the external identity. On the first encounter with that identity, the First Broker Login flow controls local account provisioning/linking. Your customization inserts rollingstone Entra Create User (Ext) into that second stage so your own Keycloak + MySQL provisioning logic executes as part of the broker lifecycle.
