Episode B • X.509 • Mutual TLS

mTLS Client Authentication

Mutual TLS (mTLS) is TLS in which both endpoints authenticate with certificates. Keycloak proves its server identity to the Java client, and the Java client presents its own X.509 certificate to Keycloak during the TLS handshake.

In this POC the client certificate is the Keycloak client credential. The token request contains no client_secret and no client_assertion.

Vocabulary

Know These Before the Commands

Certificate Authority

The lab CA signs the Keycloak server certificate and the client certificate. Its certificate becomes the trust anchor.

X.509 Certificate

Binds a public key to an identity. The client certificate uses CN=x509-cert-client.

Private Key

Stays with its owner and proves possession cryptographically. It never needs to cross the network.

Keystore

The client's PKCS12 contains its private key and certificate so Java can present them during TLS.

Truststore

Contains trusted CA certificates. It answers “which certificate issuers do I trust?”

Subject DN

Identifies the certificate subject. Keycloak's X.509 authenticator matches it to CN=x509-cert-client.

Real Java

Build the SSLContext

The KeyManager supplies client identity material. The TrustManager supplies the CA trust used to validate Keycloak.

public SSLContext buildSslContext() throws Exception {
    KeyStore keyStore = KeyStore.getInstance("PKCS12");
    try (FileInputStream fis = new FileInputStream(keystorePath)) {
        keyStore.load(fis, keystorePassword.toCharArray());
    }
    KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
    kmf.init(keyStore, keystorePassword.toCharArray());

    KeyStore trustStore = KeyStore.getInstance("PKCS12");
    try (FileInputStream fis = new FileInputStream(truststorePath)) {
        trustStore.load(fis, truststorePassword.toCharArray());
    }
    TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
    tmf.init(trustStore);

    SSLContext sslContext = SSLContext.getInstance("TLS");
    sslContext.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);
    return sslContext;
}

Commands Explained

Certificate Generation, Concept by Concept

The CA is the trust anchor. Its private key signs certificates; its certificate is imported as trusted CA material.

openssl genrsa -out ca-key.pem 4096
openssl req -x509 -new -nodes -key ca-key.pem -sha256 -days 3650 \
  -out ca-cert.pem -subj "/CN=jpa-demo-lab-ca"

The server certificate lets the Java client authenticate Keycloak. The SAN supports hostname verification for localhost and 127.0.0.1.

openssl genrsa -out kc-server-key.pem 2048
openssl req -new -key kc-server-key.pem -out kc-server.csr -subj "/CN=localhost"
openssl x509 -req -in kc-server.csr -CA ca-cert.pem -CAkey ca-key.pem -CAcreateserial \
  -out kc-server-cert.pem -days 825 -sha256 \
  -extfile <(printf "subjectAltName=DNS:localhost,IP:127.0.0.1")

This is the identity presented by the Java client. The CN intentionally matches the Keycloak client configuration.

openssl genrsa -out x509-cert-client-key.pem 2048
openssl req -new -key x509-cert-client-key.pem -out x509-cert-client.csr -subj "/CN=x509-cert-client"
openssl x509 -req -in x509-cert-client.csr -CA ca-cert.pem -CAkey ca-key.pem -CAcreateserial \
  -out x509-cert-client-cert.pem -days 825 -sha256

Java needs the client private key and certificate available through a keystore.

openssl pkcs12 -export -inkey x509-cert-client-key.pem -in x509-cert-client-cert.pem \
  -certfile ca-cert.pem -name x509-cert-client \
  -out x509-cert-client-keystore.p12 -passout pass:changeit

The truststore contains the CA certificate, not the client's private identity key.

keytool -importcert -alias jpa-demo-lab-ca -file ca-cert.pem \
  -keystore truststore.p12 -storetype PKCS12 -storepass changeit -noprompt

Key Takeaway

mTLS Moves Client Identity Proof into the TLS Handshake

The keystore gives the Java client its certificate and private key; the truststore lets it trust Keycloak. Keycloak's HTTPS listener requests and validates the client certificate. The X.509 client authenticator maps that certificate identity to x509-cert-client. Only then does the application-level client_credentials token request proceed—with no client secret and no signed JWT assertion in the form body.
