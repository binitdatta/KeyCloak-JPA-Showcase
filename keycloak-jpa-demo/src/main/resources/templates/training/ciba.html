OIDC CIBA Backchannel Authentication.

CIBA stands for Client Initiated Backchannel Authentication . The client already knows which human it wants authenticated and asks the OpenID Provider to initiate authentication through that person's separate Authentication Device.

No authorization code is typed into the client. Instead, the authentication request travels through a backchannel, the human approves or denies it elsewhere, and the client waits asynchronously for the result.

Core Concept

What Problem Does CIBA Solve?

CIBA separates the application requesting authentication from the device on which the human actually authenticates. That makes it useful when the client already knows the target user but should not collect that user's credentials itself.

Step 1

Client Knows the User

The client begins with an identifier such as login_hint=alice.

Step 2

OP Initiates Authentication

Keycloak sends a backchannel notification toward the user's Authentication Device.

Step 3

Human Decides

The human authenticates and approves or denies the request on a separate device.

Critical Distinction

CIBA vs. Device Authorization

Both flows allow a person to authenticate somewhere other than the originating client. The important difference is who initiates the human interaction.

Device Authorization

User Goes to the Authentication Experience

The device displays a user code and verification URL.

Device → shows code → User → opens browser → Keycloak

The originating device waits while the human goes elsewhere and completes authentication.

CIBA

Authentication Experience Goes to the User

The client identifies the person and asks the OP to initiate authentication toward that person's Authentication Device.

Client → identifies user → Keycloak → notifies → User's Device

There is no short user code for the person to copy from the originating client.

Architecture

The Three Components in Our POC

CIBA adds a component that the Device Grant demonstration did not need: an Authentication Device capable of receiving the backchannel notification and returning the human decision.

Keycloak Configuration

Two Different CIBA Configuration Layers

One of the important findings in the POC is that enabling CIBA on the client is not enough. Keycloak also needs to know where its Authentication Channel Provider should send the notification.

Realm / Client Configuration

CIBA Capability and Policy

Configuration inside Keycloak controls whether the client may use CIBA and governs CIBA behavior such as timing and delivery-mode related policy.

This configuration does not by itself tell Keycloak where the external Authentication Device is located.
Keycloak Server Configuration

Authentication Channel URI

In this POC, the notification destination is supplied when Keycloak starts. 

--spi-ciba-auth-channel-ciba-http-auth-channel-http-authentication-channel-uri=
http://localhost:8092/ciba/notify
End-to-End Protocol

Follow the Complete CIBA Conversation

The important architectural feature is asynchronous decoupling: Keycloak can acknowledge the client's authentication request before the human has made any decision.

Transaction Correlation

Understand auth_req_id

CIBA is asynchronous, so Keycloak needs a way for the client to refer back to the authentication transaction that was started earlier.

01

Request Created

The client submits the CIBA authentication request containing the target user's login_hint.

02

auth_req_id Returned

Keycloak returns an opaque value representing that pending CIBA authentication transaction.

03

Client Polls With It

The client presents the same auth_req_id to ask whether the human authentication has completed.

Why the POC Writes It to a File

The observed auth_req_id was more than 900 characters. The demonstration therefore stores the initialization response in /tmp/ciba_init.json and extracts the value programmatically during polling rather than manually copying it through a terminal.

Do Not Confuse These

Two Different Bearer Tokens Appear

The backchannel notification token and the final OAuth access token participate in the same overall CIBA transaction, but they have completely different purposes.

Notification / Callback

Authentication Channel Bearer Token

Keycloak sends a bearer token with the Authentication Device notification.

In this POC, the service keeps that token so it can authenticate the subsequent callback to Keycloak.

This token set represents the successful authentication outcome for the human user.

OpenID Connect

Why Did This Test Return an ID Token?

The CIBA initiation request in this demonstration explicitly requested the openid scope. 

-d "scope=openid"

The resulting response contained an id_token in addition to the access and refresh tokens. In the earlier Device Grant test, scope=openid was not requested, so that particular test did not produce an ID token.

Real Debugging Evidence

Three Bugs We Hit Building the POC

These are particularly useful teaching material because each failure initially looked like a different class of problem. The actual causes only became clear after examining concrete protocol and server evidence.

Observed Symptom Initially Looked Like Actual Cause in Our POC Lesson
Unexpected response from authentication device Connectivity problem Our /ciba/notify endpoint returned HTTP 200. The tested Keycloak HttpAuthenticationChannelProvider expected 201. An endpoint can be reachable and still violate the implementation's expected HTTP contract.
HTTP 415: Content-Type 'application/json' is not supported CORS or malformed headers Our controller expected application/x-www-form-urlencoded, while the live Keycloak notification arrived as JSON. Inspect the actual request received by the server rather than assuming the wire format.
{"error":"unsupported_grant_type"} Broken auth_req_id The polling request mistakenly used the Device Authorization grant URN. CIBA uses: urn:openid:params:grant-type:ciba Similar asynchronous OAuth flows do not imply identical grant-type identifiers.
Troubleshooting

Diagnose CIBA Layer by Layer

Because several actors participate in CIBA, debugging is much easier when each boundary is tested separately.

Confirm that the Spring Boot Authentication Device is already running and that Keycloak was started with the correct Authentication Channel URI. Test the network path before investigating OAuth claims.

Inspect the HTTP status returned by /ciba/notify. In the tested POC, returning 200 produced an unexpected-response error while returning 201 matched the behavior expected by the Keycloak implementation being tested.

Inspect the actual request Content-Type. The live test showed Keycloak sending application/json, so a Spring controller restricted to form-urlencoded input rejected the request.

This is an expected state while the human decision is outstanding. Verify that the Authentication Device received the request and that the approval callback has actually reached Keycloak.

Verify that the request uses the CIBA grant type: 
grant_type=urn:openid:params:grant-type:ciba

Do not substitute the Device Authorization grant type simply because both flows involve polling.

Verify that the POC retained the bearer token sent by Keycloak with the original Authentication Device notification and supplied that token on the callback. This is a different concern from the final OAuth access token issued for Alice.
Enterprise Interpretation

Why CIBA Is Architecturally Interesting

The POC is intentionally simple, but it demonstrates several architectural characteristics that matter in larger systems.

Decoupled Actors

The client requesting authentication does not have to be the device on which authentication occurs.

Backchannel

Authentication initiation can move through server-to-server infrastructure rather than relying entirely on browser redirects.

Asynchronous

Request delivery and human approval are separate events that can occur at different times.

Human Identity

The final OAuth/OIDC token represents the person who successfully completed authentication.

Key Takeaway

CIBA Moves Authentication Away from the Requesting Client

The client knows who it needs authenticated, but it does not perform that human authentication itself.

The client initiates a CIBA request with Keycloak. Keycloak creates a pending transaction and sends a backchannel notification to the Authentication Device. The human makes the decision there. The Authentication Device returns the decision to Keycloak, and the original client eventually obtains the OAuth/OIDC token set representing the authenticated human. The difficult part of the POC was therefore not simply turning on a Keycloak switch—it was making the Keycloak ↔ Authentication Device contract work correctly from end to end.
