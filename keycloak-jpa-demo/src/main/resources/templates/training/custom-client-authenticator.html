Custom Client Authenticator.

Keycloak already provides several client authentication mechanisms. But its Service Provider Interface allows us to extend the server with our own ClientAuthenticator implementation.

In this POC, the client sends its shared secret through the custom X-rollingstone-Client-Key HTTP header rather than through the standard client_secret form parameter.

Objective

What Are We Building?

The goal is to add another option to Keycloak's Client Authenticator selection by implementing a custom Keycloak provider. The OAuth client still has a shared secret, but the mechanism used to deliver and validate that secret is controlled by our custom Java code.

Input

Custom HTTP Header

Instead of receiving: 

client_secret=<secret>

the provider reads: 

X-rollingstone-Client-Key: <secret>
Processing

Keycloak SPI

Our implementation of ClientAuthenticator participates directly in Keycloak's client authentication processing.

The provider reads the custom header, obtains the configured client secret and evaluates whether the credentials match.

Result

Success or Failure

When validation succeeds, the authenticator calls: 

context.success();

Invalid or missing credentials cause the authentication attempt to fail.

Extension Point

Built-In Authentication vs. Our Custom Provider

We are not replacing Keycloak's token endpoint or OAuth processing. We are extending one specific decision point: how Keycloak authenticates the OAuth client.

Mechanism Credential How It Reaches Keycloak Validation Mechanism

Code Walkthrough

Understand the Provider One Component at a Time

This is the runtime authentication implementation. Its responsibility is deliberately narrow:
  • access the client-authentication context,
  • inspect the incoming request,
  • read X-Havi-Client-Key,
  • obtain the configured client credential,
  • validate the submitted credential,
  • signal success or failure. 
Client Request
      │
      ▼
CustomSecretHeaderClientAuthenticator
      │
      ├── Read X-Havi-Client-Key
      │
      ├── Obtain configured secret
      │
      ├── Validate
      │
      └── context.success() / failure()

The factory represents the provider to the Keycloak runtime. In this POC its provider identity is: 
havi-secret-header

Conceptually, the factory answers questions such as: What is this provider? What identifier should Keycloak use for it? How should an authenticator instance be obtained?

The service registration file is named: 
META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory

It identifies the implementation of the factory contract contained in the provider JAR.

Without provider discovery, writing a perfectly valid factory class is not sufficient to make the custom authenticator appear in Keycloak.

The Maven build packages the implementation and its provider metadata together. That JAR is copied to: 
$KEYCLOAK_HOME/providers/

The important architectural boundary is that this code becomes part of the Keycloak server runtime.

Security Interpretation

What This POC Changes — and What It Does Not

A custom header changes the credential transport convention used by the client and the server-side validation logic. It does not transform a shared secret into an asymmetric credential.

Still a Shared Secret

Both the client and Keycloak rely on knowledge of the same secret value.

HTTPS Is Essential

A secret placed in a custom HTTP header is still sensitive credential material and must be protected in transit.

Do Not Log the Header

Application servers, reverse proxies, API gateways and diagnostic middleware should not expose the custom secret header in logs.

Important Architectural Lesson

This POC is valuable because it demonstrates Keycloak extensibility. The important concept is not that a proprietary header is inherently stronger than the standard OAuth client-secret mechanisms. The lesson is that Keycloak exposes an SPI through which specialized client-authentication behavior can be integrated when an enterprise has a legitimate requirement for it.

Troubleshooting

When Havi Secret Header Does Not Appear

Debug the provider from deployment outward rather than starting with the OAuth token request. 

cd custom-providers/client-authenticator
mvn clean package

ls -l target/

Confirm that the expected provider JAR actually exists before investigating Keycloak. 

ls -l $KEYCLOAK_HOME/providers/

The custom provider must be available to the Keycloak runtime.

Inspect the JAR and confirm that it contains: 
META-INF/services/
org.keycloak.authentication.ClientAuthenticatorFactory

The factory class can compile successfully while still remaining undiscoverable if the service registration is missing or incorrect. 

cd $KEYCLOAK_HOME

bin/kc.sh build
bin/kc.sh start-dev

Check startup output for provider-related exceptions before opening the Admin Console.

Verify the request in layers:
  • correct client_id,
  • client configured for Havi Secret Header,
  • X-Havi-Client-Key actually present,
  • correct secret value,
  • correct OAuth grant type,
  • no intermediary removing the custom header.

Check whether the reverse proxy, ingress controller, WAF or API gateway forwards X-Havi-Client-Key to Keycloak.
Do not solve the problem by indiscriminately logging request headers. This header contains credential material.

Key Takeaway

The SPI Lets Us Extend Keycloak at the Client-Authentication Boundary

We did not write our own OAuth authorization server and we did not replace Keycloak's token endpoint.

We implemented a focused Keycloak extension: one authenticator, one factory and one provider registration. The client sends its shared credential through X-Havi-Client-Key, the custom ClientAuthenticator validates it, and successful validation hands control back to Keycloak through context.success(). That small extension demonstrates an important enterprise capability: when a legitimate integration requirement cannot be satisfied by a built-in mechanism, Keycloak's SPI model allows carefully scoped server-side behavior to be added without rebuilding the entire identity platform.
